# Case Study Evidence Standard

This guide defines the public documentation standard for portfolio case studies in this repository.

## Purpose

A case study should make it possible to understand what was built, which design choices were made, and what evidence supports the outcome. It should not read as a task list or make claims beyond the evaluated scope.

## Required sections

Each published case study should clearly distinguish:

1. **Problem and users**: the practical problem, target user, and relevant constraints.
2. **Scope and contribution**: the work included in the project and the author's specific role.
3. **System design**: the workflow, components, tool or data boundaries, and material trade-offs.
4. **Evaluation evidence**: the test set or scenario, metric definition, comparison condition, and measured result.
5. **Limitations and safeguards**: known failure modes, safety constraints, human review, or unresolved work.

## Evidence policy

- Label measured results, design targets, and future work separately.
- State the denominator and evaluation condition for a percentage or benchmark result.
- Do not describe a prototype, mockup, or limited evaluation as a deployed product.
- Keep implementation details reproducible when they can be shared safely.
- Exclude credentials, customer data, internal documents, and non-public implementation details.

## Publication checklist

Before publishing an update:

- Verify that technical claims match a source artifact or recorded evaluation.
- Confirm that English and Korean portfolio content remain consistent where both are shown.
- Check links and visible numerical claims.
- Review the content for confidential or personal information.
